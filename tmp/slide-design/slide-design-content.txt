SLIDE 03
**1.1. Challenges in AI-Assisted Development**

An ambiguous requirement leaves important product decisions unresolved.

**Initial request: “Allow administrators to publish a lesson.”**

| Missing decision | Possible product failure |
| --- | --- |
| Must the lesson contain segments? | A learner opens an empty lesson. |
| Must every segment and media asset be ready? | Incomplete or unapproved content becomes available. |
| What happens when two admins update the lesson? | A stale change may overwrite a newer decision. |

AI may choose an implementation for these unspecified cases. Working code alone does not demonstrate correct behavior.

**Control requirement:** Define the conditions, rejected cases, and expected outcomes.
LAYOUT: Đặt câu yêu cầu ban đầu ngay dưới tiêu đề. Bảng ba hàng ở giữa làm nội dung chính. Dưới bảng dùng một dải chữ kết luận gồm hai câu cuối. Nếu có chỗ, đặt nhãn nhỏ 'F04: Content Administration' cạnh câu yêu cầu để gắn với dự án. Không cần ảnh AI trang trí vì bảng đã mang nội dung.

SLIDE 04
**1.2. What Is a Specification?**

A specification defines the behavior, constraints, and acceptance conditions that stakeholders agree the system must satisfy.

| Element | Example in Schinese |
| --- | --- |
| Actor | An authorized administrator |
| Action | Publish a Free lesson |
| Preconditions | Published topic, at least one segment, all segments published, all referenced media approved |
| Expected result | The lesson becomes published when all conditions hold |
| Rejection behavior | Invalid conditions leave the lesson unpublished |
| Acceptance evidence | Scenarios and tests for accepted and rejected publication |

A feature specification connects user intent to design and verification. Detailed API and data contracts can live in linked documents.
LAYOUT: Tiêu đề ở trên, định nghĩa một hoặc hai dòng ngay dưới. Bảng chiếm khoảng 70% chiều cao phần còn lại. Làm nổi các từ Actor, Preconditions, Expected result để người xem theo cấu trúc. Câu cuối ở đáy giải thích vì sao dự án có nhiều file đặc tả.

SLIDE 05
**1.3. Three Levels of Correctness**

A reliable conclusion about product quality requires evidence at more than one level.

| Level | Schinese question | Required evidence |
| --- | --- | --- |
| Correct need | Can learners find suitable content and practise effectively? | User feedback and domain review |
| Correct implementation | Does publication reject missing segments and unapproved media? | Requirement-based review and tests |
| Correct operation | Do access and data rules hold during concurrent changes or provider failure? | Integration, concurrency, and operational checks |

A passing publication test supports a defined behavior. It does not measure learning effectiveness or prove the whole product is reliable.

**Current focus:** Traceable implementation and selected verification evidence.
LAYOUT: Dùng ba hàng ngang có độ cao bằng nhau. Mỗi hàng đi từ câu hỏi đến phép kiểm chứng, giúp người xem so sánh trực tiếp. Đặt câu giới hạn kết luận dưới bảng. Không vẽ phần trăm hay điểm trưởng thành vì chưa có số đo toàn dự án.

SLIDE 08
**2.3. Complexity Behind One AI Buddy Message**

A learner expects one useful reply. The system must coordinate ownership, allowance, retries, and failures.

**Illustrative request:** “Help me practise greeting someone in Chinese.”

| Situation | Required behavior |
| --- | --- |
| Valid message in the learner's active conversation | Return a valid reply and consume one allowance unit |
| Another user's conversation | Reject access |
| No remaining allowance | Stop before provider processing |
| Same logical message sent again | Prevent a second charge and duplicate reply |
| Provider timeout or invalid output | Return a safe final result and restore reserved allowance exactly once |

**Hard case:** Concurrent retries must preserve these rules while sharing the original request's deadline.

Design requirements from F11, not a completed E2E demonstration.
LAYOUT: Đặt message mẫu ở đầu, bảng tình huống ở giữa. Dòng 'Hard case' đặt cuối để chuyển từ tình huống thông thường sang vấn đề đồng thời. Nếu dựng flow, thêm một nhánh retry quay về yêu cầu cũ. Không vẽ mỗi retry thành lần gọi provider mới.

SLIDE 10
**3.2. Specification Readiness Criteria**

A feature is ready to implement when its important decisions and acceptance conditions are clear.

**Readiness questions**

- Who owns the requirement and reviews changes?
- Are actors, permissions, scope, and exclusions explicit?
- Are failure cases and acceptance scenarios defined?
- Does the feature agree with architecture, API, and data contracts?
- Are dependencies and the effective specification version known?

**Recorded Schinese clarification**  
How can learners receive Premium when automated billing is outside the MVP?

**Decision**  
The MVP provides Free access. Paid Premium activation and upgrade journeys remain deferred.

**Effect**  
Catalog behavior, content access, and allowance rules must follow the same scope.
LAYOUT: Chia hai cột: bên trái 55% là câu hỏi readiness, bên phải 45% là ví dụ clarification thật gồm vấn đề, quyết định, tác động. Phân biệt hai vùng bằng khoảng trắng hoặc một đường kẻ mảnh. Nếu dùng ảnh trích file, chỉ lấy phần clarification và ghi tên nguồn.

SLIDE 11
**3.3. Controlling Development Outputs**

Every handoff should produce an artifact that the next stage can inspect and use.

| Handoff | Expected output | Review condition |
| --- | --- | --- |
| Specification to design | Plan, data model, and API contract | Required behavior has a feasible design within project boundaries |
| Design to tasks | Dependency-ordered implementation and verification tasks | Each task has a clear purpose and expected result |
| Tasks to code | Source changes and related contract updates | Review finds the required logic and no unintended scope change |
| Code to acceptance | Test results and reproducible scenarios | Evidence supports the agreed acceptance conditions |

**F04 example:** A publish button is only one output. Publication rules, safe errors, and rejected scenarios also require implementation and verification.

Automation of blocking gates remains a proposed improvement.
LAYOUT: Dùng bảng bốn hàng với cột Review condition rộng nhất. Dưới bảng đặt ví dụ F04 để giải thích cụ thể một đầu ra hay bị bỏ sót. Có thể đánh số các handoff thay vì vẽ nhiều mũi tên chen giữa chữ.

SLIDE 12
**3.4. Levels of Verification Evidence**

The strength of a claim depends on the evidence available for that specific requirement.

1. **Specified:** The requirement and acceptance conditions exist.
2. **Mapped:** The requirement connects to design, tasks, and implementation.
3. **Tested:** Relevant tests ran on an identified version and produced recorded results.
4. **Integrated:** API, database, and user-journey checks verify interactions.
5. **Evaluated in use:** User or operational evidence supports product outcomes.

**Schinese evidence example**  
Selected F04 publication checks have source mappings and passing unit tests.

**Remaining boundary**  
Those results alone do not establish catalog integration, concurrent database behavior, or learning effectiveness.

This is a proposed reporting framework, not a measured maturity score for the entire project.
LAYOUT: Dùng một thang dọc năm hàng, mỗi hàng có nhãn và một câu định nghĩa. Bên phải đặt ví dụ F04 và phạm vi còn thiếu. Không tô cả năm mức thành đạt. Có thể đánh dấu mức Tested cho đúng các case đã chạy và ghi rõ 'selected checks'.

Each feature moves through a reviewable cycle with explicit outputs and feedback.

| Stage | Work performed | Concrete output |
| --- | --- | --- |

SLIDE 15
**4.3. Writing Testable Requirements**

A useful requirement identifies the trigger, preconditions, expected behavior, and rejection conditions.

**Initial request**  
“An administrator can publish a lesson.”

**Refined requirement**  
When an authorized administrator requests publication using the current version, the system shall publish the lesson only if all publication conditions hold.

**Publication conditions in F04**

- The parent topic is PUBLISHED.
- The lesson has FREE access and at least one segment.
- Every segment is PUBLISHED.
- Every referenced media asset is APPROVED.
- The lesson is not ARCHIVED.

**Failure behavior**  
Reject invalid publication or a stale version without applying the requested state change.

Presentation synthesis of FR-001, FR-003, FR-004, FR-005, and FR-007.
LAYOUT: Bố trí câu yêu cầu ngắn bên trái khoảng 30%, nội dung đã làm rõ bên phải khoảng 70%. Dùng dấu ngoặc hoặc đường nối để chỉ phần thông tin được bổ sung: actor, trigger, condition, result. Danh sách điều kiện phải đọc được, không thay bằng chữ 'valid' hoặc 'ready'.

SLIDE 16
**4.4. Defining Acceptance Scenarios**

Acceptance scenarios turn publication rules into observable checks.

| Given | When | Then |
| --- | --- | --- |
| A draft Free lesson meets every publication condition | An admin publishes with the current version | The lesson becomes PUBLISHED |
| A draft lesson has no segments | An admin requests publication | Reject and preserve its state |
| One associated segment remains DRAFT | An admin requests publication | Reject and preserve the lesson state |
| A referenced media asset is not APPROVED | An admin requests publication | Reject and preserve the lesson state |
| The request contains an old version | An admin requests an update | Return a conflict and require a reload |

**Evidence boundary:** The selected unit suite exercises the first three scenarios. Media approval and API conflict behavior require additional case-level verification.
LAYOUT: Dùng bảng Given–When–Then là trung tâm, cột When hẹp vì hành động lặp lại. Đặt ghi chú phạm vi kiểm chứng phía dưới. Khi trình bày, highlight từng hàng theo thứ tự và dùng từ 'all' ở hàng đầu để dẫn tới các tình huống thiếu điều kiện.

SLIDE 17
**4.5. Specification Depth Based on Risk**

The required depth depends on failure impact and the complexity of the behavior.

| Depth | Schinese example | What to define |
| --- | --- | --- |
| Sketch | Format a practice duration for display | Inputs, outputs, and representative examples |
| Detailed | Update profile preferences or filter a list | Validation, states, errors, and acceptance scenarios |
| Detailed with explicit states and invariants | Account permissions, AI allowance, lesson publication | Allowed transitions, concurrency rules, ownership, and recovery behavior |

**Selection questions**

- What happens to the learner or data if this is wrong?
- How many branches and state changes must remain consistent?
- Which other features depend on the decision?

A state diagram improves precision. It does not by itself constitute formal verification.
LAYOUT: Dùng bảng ba mức và một cụm ba câu hỏi ngắn phía dưới. Nhãn mức cao cần ghi đầy đủ về state và invariant để người xem không hiểu Formal là chứng minh toán học. Nên tô đậm các ví dụ quota và publication vì sẽ xuất hiện ở phần bằng chứng.

SLIDE 19
**5.2. Responsibility and Enforcement Boundaries**

The backend is responsible for decisions that depend on identity, shared state, and product rules.

| Rule | Enforcement owner | Product example |
| --- | --- | --- |
| ADMIN and resource ownership | Backend services | Learners cannot publish content or read another user's chat |
| Publication prerequisites | Content services | A lesson requires published segments and approved media |
| Allowance and logical retries | Backend with transaction and data safeguards | One eligible message must not consume quota twice |
| AI response generation | ai-service | Produce a reply for the selected learning activity |
| Output acceptance and persistence | Backend, with service-side validation | Reject an invalid AI result before saving it |
| Loading, errors, and recovery | React using backend responses | Explain a conflict and let the admin reload |

**Architecture rationale:** Keep related business decisions within the modular backend and isolate provider orchestration behind a private contract.
LAYOUT: Dùng bảng ba cột, cột ví dụ rộng nhất. Tô đậm tên nơi chịu trách nhiệm để thấy nhóm quy tắc nằm ở backend. Dưới bảng đặt lý do kiến trúc hai dòng. Không cần lặp lại sơ đồ ở slide 18. Khi nói, trỏ vào hàng quyền và hàng quota trước vì đây là hai ranh giới quan trọng nhất.

SLIDE 20
**5.3. AI Input and Output Control**

F11 defines a bounded learning conversation with checks before provider work and before persistence.

| Stage | Required control |
| --- | --- |
| Receive | Validate identity, conversation ownership, logical retry, and rate limit |
| Check input | Allow plain text within the selected Chinese-learning activity |
| Reserve and dispatch | Reserve allowance once and send only the permitted context through the private contract |
| Validate output | Check structure and content before accepting the response |
| Complete | Save a valid message pair or return a safe failure with exactly-once allowance restoration |

**Limits defined in the spec**

- At most 1,000 characters per learner message.
- At most 10 completed prior messages from the same conversation.
- Five send attempts per rolling minute. Logical retries do not add an attempt.
- A terminal result within the original 30-second deadline.

Required reply: Chinese response, concise Vietnamese explanation, and at most one practice suggestion.

These are design requirements, not measured production guarantees.
LAYOUT: Dùng bảng hoặc flow năm bước ở khoảng 60% bên trái và danh sách bốn giới hạn ở 40% bên phải. Dòng cấu trúc reply đặt dưới cả hai vùng để thể hiện output. Ghi rõ 'Defined in F11' cạnh các số. Khi dùng flow, mỗi ô chứa Stage và Required control tương ứng, không cần giữ bảng trùng nội dung.

SLIDE 23
**6.3. Detecting Specification–Implementation Drift**

Drift appears when requirements, design, tasks, code, and verification no longer describe the same behavior.

| Drift pattern | F04 evidence or review concern |
| --- | --- |
| A rule is incompletely implemented | T025 records the need to enforce all publication conditions |
| Implementation conflicts with shared rules | T022 records an access-token storage correction |

**7.1. AI-Generated Functions and Algorithm Optimization**

A specification constrains behavior, but often leaves internal algorithms and helper functions open to implementation choices.

**Where control can become weaker**

- AI may add helpers, change data structures, or reuse intermediate results while attempting an optimization.
- New code may introduce assumptions, side effects, or failure paths that have not been reviewed.
- Existing functional tests may pass without covering changed state or larger inputs.

**Hypothetical F04 example**

1. A helper stores a successful publication-readiness check.
2. A referenced media asset later becomes QUARANTINED.
3. Reusing the old result could accept an invalid publication unless the design handles invalidation.

**Key limitation:** Passing examples do not prove complete behavioral coverage or improved performance.

Illustrative scenario only. No such optimization defect is claimed as observed in Schinese.
LAYOUT: Chia trái 45% cho ba rủi ro, phải 55% cho ví dụ ba thời điểm. Viết trạng thái APPROVED rồi QUARANTINED trên một timeline và chỉ rõ kết quả cũ được dùng lại ở đâu. Nhãn 'Hypothetical example' phải nằm cạnh ví dụ, không giấu trong speaker notes. Câu giới hạn đặt cuối slide.

SLIDE 27
**7.2. Review and Verification of Optimization Changes**

An optimization claim needs both preserved behavior and measured improvement under defined conditions.

| Review question | Evidence to inspect |
| --- | --- |
| What problem does the new function solve? | Linked task, callers, and the source diff |
| What assumptions or side effects does it introduce? | Inputs, outputs, state changes, and error paths |
| Which rules must remain true? | Ownership, publication conditions, quota, and retry invariants |
| What happens as input size increases? | Complexity analysis and representative workloads |
| Is the change actually faster or cheaper? | Before/after measurements in the same environment |

**Acceptance rule**  
Preserve required behavior, review significant algorithm decisions, and measure the intended improvement.

**Remaining limit**  
Tests and benchmarks cover defined cases and workloads. They do not establish correctness for every possible situation.
LAYOUT: Bảng hai cột là trọng tâm, câu hỏi ngắn bên trái và bằng chứng bên phải. Câu Acceptance rule đặt dưới bảng với các động từ quan trọng in đậm. Không đưa số tốc độ cải thiện nếu chưa đo. Trong lời nói có thể trỏ lại ví dụ slide 26 nhưng không lặp hình.

**A5. Methodology Questions**

Specification control must include human judgment, independent checks, and managed change.

| Question | Defensible answer |
| --- | --- |
| Who validates the specification? | The requirement owner and domain reviewers, supported by concrete scenarios and user feedback |
| Does this become Waterfall? | Work in bounded features and revise the baseline through reviewed feedback |
| Why can passing tests still miss a defect? | Tests may omit a case or share the implementation's mistaken assumption |
| Is more specification always better? | Choose depth according to risk and include writing and review in the effort cost |
| What is distinctive about using specs with AI? | Structured context guides agent execution, while traceability and review check its output |

A specification organizes decisions. Its quality and enforcement still require evidence.
